# STM32H7 FreeRTOS/lwIP XCP CRM Debug Checklist

Context: sporadic invalid XCP command response transport headers (`dlc`/`ctr`) were observed on an STM32H7 project generated by STM32CubeMX with FreeRTOS and lwIP. The XCPlite CRM response path builds a small `tXcpCtoMessage` and sends it via `sendto`/lwIP.

## Main Suspicion

On STM32H7, first suspect Ethernet DMA/cache/MPU/lwIP configuration before blaming the XCPlite stack buffer.

STM32H7 has data cache and several memory regions. Ethernet DMA cannot access every RAM region, and cached memory must be handled carefully. A wrong MPU/cache/DMA setup can make the CPU write correct data while the Ethernet DMA later transmits stale or corrupted data. This can look exactly like random bad `dlc` or `ctr` bytes.

## Immediate Experiments

1. Temporarily replace the stack CRM buffer in `XcpTlSendCrm()` with a static/global buffer protected by the existing `ctr_mutex`.

   ```c
   static tXcpCtoMessage crm_tx_buf;
   ```

   If the problem disappears, suspect stack overwrite, bad task stack sizing, or an unusual lwIP/buffer lifetime issue.

2. Add instrumentation immediately after filling the CRM header and immediately before/after `lwip_sendto()`.

   Log:

   - buffer address
   - `dlc`
   - `ctr`
   - first bytes of packet
   - return value from `lwip_sendto`
   - `errno` on failure

3. Increase stack sizes as a test.

   Increase:

   - XCP receive/command task stack
   - XCP transmit task stack, if separate
   - `tcpip_thread` stack
   - default lwIP/FreeRTOS thread stack

4. Enable FreeRTOS diagnostics.

   Check:

   - `configCHECK_FOR_STACK_OVERFLOW`
   - `configASSERT`
   - task high-water marks
   - heap remaining / minimum ever free heap

## CubeMX / lwIP Settings To Check

Inspect generated `lwipopts.h`.

Important settings:

- `NO_SYS == 0`
- `LWIP_SOCKET == 1`
- `LWIP_NETCONN == 1`
- `LWIP_UDP == 1`
- `MEM_SIZE` large enough
- `PBUF_POOL_SIZE` large enough
- `PBUF_POOL_BUFSIZE` suitable for Ethernet frames
- `MEMP_NUM_PBUF`
- `MEMP_NUM_UDP_PCB`
- `MEMP_NUM_SYS_TIMEOUT`
- `TCPIP_THREAD_STACKSIZE`
- `DEFAULT_THREAD_STACKSIZE`
- `TCPIP_MBOX_SIZE`
- `DEFAULT_UDP_RECVMBOX_SIZE`

Search generated code for dangerous or suspicious options:

```c
PBUF_NEEDS_COPY
PBUF_REF
PBUF_ROM
NETCONN_NOCOPY
LWIP_NETIF_TX_SINGLE_PBUF
ETH_TX_BUFFER
ETH_RX_BUFFER
LWIP_MEMPOOL_DECLARE
```

Big red flag:

```c
#define PBUF_NEEDS_COPY(p) 0
```

That can allow lwIP to keep references to mutable buffers instead of copying data that must live longer than the call stack.

## STM32H7 Ethernet DMA / Cache / MPU Checks

Check CubeMX and generated code:

- ETH DMA descriptors must be in DMA-accessible RAM.
- ETH RX/TX buffers must be in DMA-accessible RAM.
- ETH descriptors and buffers must not be placed in DTCM.
- Linker script should place Ethernet/LwIP buffers in the intended RAM section.
- MPU should mark DMA buffer regions non-cacheable, or driver must perform correct D-cache clean/invalidate operations.
- If D-cache is enabled, generated `ethernetif.c` must correctly clean TX buffers before DMA reads them and invalidate RX buffers after DMA writes them.

Typical H7 failure mode:

- CPU writes correct CRM header.
- Header remains only in D-cache.
- Ethernet DMA reads old/stale RAM contents.
- Network trace shows corrupted `dlc`/`ctr`.

## CubeMX Areas To Inspect

In CubeMX:

- `Middleware -> LwIP`
- `System Core -> FreeRTOS`
- `System Core -> MPU`
- `Connectivity -> ETH`

Verify:

- LwIP is configured for RTOS mode.
- Socket API is enabled.
- UDP is enabled.
- ETH checksum handling matches the generated driver and hardware offload settings.
- ETH DMA descriptor count and buffer count are sane.
- ETH buffer size is suitable.
- Thread stack sizes are not tiny.
- Memory placement matches ST examples for the same STM32H7 board/family.

## Code Cleanup Worth Doing

In the FreeRTOS/lwIP `socketSendTo()` implementation, avoid unaligned/aliasing-sensitive loads like:

```c
dst.sin_addr.s_addr = *(uint32_t *)addr;
```

Prefer:

```c
memcpy(&dst.sin_addr.s_addr, addr, 4);
```

This is probably not the main H7 corruption cause, but it is cleaner and safer.

## Priority Order

1. Check H7 ETH DMA buffer placement, linker script, MPU, and D-cache handling.
2. Compare `ethernetif.c`, linker script, and MPU setup with an official ST example for the same H7 board or MCU family.
3. Check `PBUF_NEEDS_COPY`, `PBUF_REF`, `NETCONN_NOCOPY`, and related zero-copy settings.
4. Increase FreeRTOS/lwIP/XCP task stacks and enable stack overflow diagnostics.
5. Increase lwIP memory pools and mailbox sizes if send/receive pressure is high.
6. Run the static CRM buffer experiment.

## Interpretation

If the static CRM buffer fixes the issue:

- stack overflow/overwrite is likely, or
- the lwIP/driver path may be retaining a pointer longer than expected.

If the static CRM buffer does not fix the issue:

- DMA/cache/MPU/lwIP memory corruption remains the top suspect on STM32H7.

For STM32H7, bad cache coherency or DMA-inaccessible Ethernet buffers are very plausible causes of sporadic corrupted Ethernet payload bytes.
