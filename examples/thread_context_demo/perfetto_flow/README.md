# Perfetto

## Chrome JSON format

The Chrome JSON trace format consists of a JSON array of event objects. Each object represents a single trace event and typically includes fields like pid (process ID), tid (thread ID), ts (timestamp in microseconds), ph (phase, indicating event type like begin, end, instant, counter, etc.), name (event name), cat (category), and args (event-specific arguments). This format was originally developed for Chrome's tracing tool.

While Chromium browser developers now primarily use Perfetto's native protobuf format for trace collection, the Chrome JSON format is still encountered in Third-party Tools & Libraries: Due to its longevity and relatively simple structure, it's often chosen for its ease of generation and established "stability" as a known format.

Chrome JSON files can be opened directly in the Perfetto UI. The UI visualizes common event types, including:

- B (begin) and E (end) events as slices.
- X (complete) events as slices.
- I (instant) events as single points on the timeline.
- C (counter) events as counter tracks.
- M (metadata) events for process and thread names, etc.
- s, t, f (flow) events as connecting arrows between slices.

These events are parsed into Perfetto's standard SQL tables (e.g., slice, track, process, thread, counter, args). 
This allows you to analyze Chrome JSON traces using SQL queries.

Notes:
- Perfetto aims to adhere to the Trace Event Format specification. 
https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU
- Perfetto's data model requires duration events (B/E pairs and X events) to nest, as mandated by the spec. 
- Overlapping, non-nested events are out of spec. 
Perfetto keeps them visible by laying them out on a separate overflow track, but the result might not match what you intended. 
- Support for some less common or highly specific features of the JSON format might be limited. 


How to Generate:
Due to its established nature and simple structure, various libraries and tools across different languages (e.g., for Node.js, Python, Java, C++) can produce trace files in the Chrome JSON format.

## State before the span links were implemented

- Contexts `SigGen1`, `SigGen2` (one per signal generator instance and its task thread), `Startup` (now `Main`) and `Mainloop` (main thread).
- `DaqSpan(name)` records begin and end of a synchronous code section on the spans event `<context>.spans` of the current context.
  A sample is the state after a span begin or end: `<context>.span` (span name, enum `conv.spans`), `<context>.level`
  (nesting level), `<context>.span_dt` (duration of the span which just ended), optionally `<context>.thread`
  (`OPTION_DAQ_SPAN_THREAD`).
- A span has a name and a nesting level, but **no identity**: no span instance id, no parent id, no relation between contexts.
- The main loop polls the current value of each generator with `Poll()`. This samples the signal, it is not the complete stream.
  The complete stream exists on the producer side only (`SigGen1.value_` on event `SigGen1.siggen`).

`xcpclient --perfetto trace.json` ([tools/xcpclient/src/perfetto_writer/mod.rs](../../../tools/xcpclient/src/perfetto_writer/mod.rs)):

- One Perfetto process per context, `pid` = context index.
- Track `spans` (`tid` 1), or one track per thread index with `<context>.thread`. Nesting is rebuilt from the level samples with
  a stack per context and thread, a slice is written as `"ph":"X"` when the span ends.
- Counter tracks (`"ph":"C"`) for numeric signals, state tracks (`tid` >= 1000) for enum signals.
- Only the record types `X`, `C` and `M` (metadata: `process_name`, `process_sort_index`, `thread_name`, `thread_sort_index`).

  **No flow events.** Since the span links, xcpclient also writes flows (`"ph":"s"` and `"ph":"f"`).



## Linking a producer span to a consumer span

Goal: Show in thread_context_demo a child span which is not in the time slot of its parent, and make the relation between them visible in Perfetto as an arrow. The use case is a signal generator task which pushes its values into a queue, and the main loop which drains the queue.

Implemented, see "Span links and Perfetto arrows" in the [demo README](../README.md). The example traces in this folder are
generated by a script, they show the idea, not a measurement.

What was implemented, compared with the analysis below:

- The link identifies the producer span by its track and a timestamp, not by a span sequence number (item 1 below is not needed):
  `xcp::SpanLink` carries the producer context id, span id, thread index and the clock at the capture.
- The link is recorded on its own event `<context>.links` of the consumer context (`xcp::LinkSpan`), not in the spans event and
  not with a naming convention in `DaqEventCtxVar` (neither A nor B below).
- The A2L file has the new enum `conv.contexts`, so xcpclient finds the process of the producer context by name.
- xcpclient writes flow format v1. The `"s"` event is placed at the capture time, inside the producer span and after its nested
  spans have ended, so it binds to that span. Nothing is kept per span in xcpclient.

Timeline of both example traces (times in us, 60 ms in total):

- `SigGen1`, `SigGen2`: span `calc` (3 ms) every 8 ms, `SigGen2` 1 ms later. Nested span `clip` (1 ms). The value is pushed
  into the queue inside `calc`, after `clip`.
- `Mainloop`: span `drain` at 13 ms and 30 ms, which process 4 queue items each, then a stall until 60 ms, which processes the
  remaining 8 items. One nested span `process` (0.8 ms) per item, with the arguments `from` and `item`.
- `Mainloop` counter `queue_len`: the number of items in the queue, rises to 8 during the stall.


## The idea: a queue between producer and consumer

The signal generator task pushes every value into a queue, the main loop drains the queue. Compared with `Poll()`, the main loop
then sees the complete stream of values.

Each item is processed after the producer span which created it has ended. So the "child outside the parent time slot" happens
by itself, a stall of the consumer is not needed. A stall (or a slow consumer) only makes the distance longer and the queue
fill level visible.

To link both sides, the queue item has to carry the identity of the producer span, in OTel terms its span context. Carrying the
`xcp::Context` alone is not enough: it tells which instance produced the item, but not which span.

## What we learned about Perfetto

Checked with the Perfetto UI v59.1 (ui.perfetto.dev).

### No implicit arrows

Perfetto does not draw arrows for parent and child spans. Nesting on one track is shown by time containment, without arrows.
An arrow is drawn only for an explicit **flow** in the trace. A flow connects two slices, it can cross tracks and processes.
So `xcpclient --perfetto` has to write flows, and the data for it has to be measured.

### Flow format v1: separate flow events

```json
{"ph":"s","pid":1,"tid":1,"name":"queue","cat":"flow","id":5,"ts":32000},
{"ph":"f","pid":3,"tid":1,"name":"queue","cat":"flow","id":5,"ts":60500,"bp":"e"},
```

- `"s"` starts the flow, `"f"` ends it, matched by `id` (with `cat` and `name`). `"t"` would be an intermediate step (not used).
- `"s"` binds to the **innermost** slice on the same `pid`/`tid` which encloses `ts`. Checked: a start at a timestamp inside
  `clip` binds to `clip`, not to the enclosing `calc`.
- `"f"` with `"bp":"e"` binds to the slice which encloses `ts`, in the same way. Checked.
- `"f"` without `"bp":"e"` binds to the next slice which begins at or after `ts`. This is from the trace event format
  description and was not checked.
- The flow events can be written at any time and in any order, independent of the slices. The writer does not need to know
  the slices, only the timestamps and tracks.

### Flow format v2: flow fields on the slices

```json
{"ph":"X","pid":1,"tid":1,"name":"calc","ts":32000,"dur":3000,"bind_id":"0x5","flow_out":true},
{"ph":"X","pid":3,"tid":1,"name":"process","ts":60100,"dur":800,"bind_id":"0x5","flow_in":true},
```

- The flow is bound to exactly this slice, no timestamp rules.
- `bind_id` as a hex string was checked. A plain number was not checked.
- The writer has to know when it writes the producer slice that a flow starts there. xcpclient writes a slice when the span
  ends, and a consumer may take the item before the producer span has ended. So `flow_out` would have to be set on every producer
  slice which may have consumers. Whether Perfetto accepts a `flow_out` without a matching `flow_in` was not checked.

Both formats can be mixed in one file. Both example files import with 16 flows and 51 slices.

**Recommendation for xcpclient: format v1.** The two flow events are written when the link is known, at the timestamps of the
producer and the consumer, without changing the slice output.

### UI behaviour

- After loading, the context tracks are collapsed and nothing is selected, **no arrows are visible**.
- Expand the tracks (expand all icon left of "Default Workspace") and **click a single slice**. Its arrows are drawn. The details
  panel lists them under "Preceding Flows" with the producer slice, the delay (from the end of the producer slice) and the thread,
  and shows the `args` of the slice.
- Clicking the producer slice should show the outgoing arrow in the same way (not checked).
- An area selection does not draw arrows. It lists the flows in the tab "Flow Events".


## The same in OTel terms

OTel has no arrow object. A span which was caused by another span stores a reference back to it:

| Reference | Stored in | Count | Meaning |
|---|---|---|---|
| Parent | `parent_span_id`, same `trace_id` | exactly one | "I am part of that operation" |
| Link | `links[]`, each a span context (`trace_id`, `span_id`) plus attributes | any | "I was caused by, or relate to, that operation" |

- The reference is **one-sided**: the producer records nothing about its consumers. In Perfetto both ends carry the flow id.
- There is no time constraint: a child may begin after its parent has ended.
- Context propagation through a queue means: the queue item carries the span context of the producer span, like the
  `traceparent` header of a network message.

The queue example:

```
SigGen1 thread:   calc       trace T1, span A, kind PRODUCER
                    push  -> queue item carries {T1, A}

Main thread:      drain      trace T2, span D, kind CONSUMER
                    process  trace T2, span P, parent D, links [{T1, A}]
```

`process` has two causes: it runs inside `drain`, and it processes an item made by `calc`. It can have one parent only:

- Parent `drain`, link to `calc`: stays in the trace of the consumer. Preferred by the OTel messaging conventions (as remembered,
  not checked), mandatory for a batch, where one span processes several items.
- Parent `calc`: `process` becomes a child of `calc` which begins after its parent has ended. Allowed for a single item.

Mapping to Perfetto:

| OTel | Perfetto |
|---|---|
| Parent, same thread, synchronous | Nesting on one track, no arrow |
| Parent in another thread or time slot | Flow (arrow), nesting is not possible |
| Link | Flow (arrow) |
| Span context carried in the queue item | Flow id |

Perfetto does not distinguish parent and link. OTel backends usually draw no arrows at all, Jaeger for example shows the parents
as an indented tree and lists the links in the span details. The arrow is the Perfetto way to display a parent or a link.

See also [docs/TIME_AND_CAUSALITY.md](../../../docs/TIME_AND_CAUSALITY.md).

## What is needed for the link between producer and consumer

1. **Span identity (library).** A span instance gets an id, for example a sequence number per context, incremented at each span
   begin. It is measured in the spans event, for example as `<context>.span_seq`. Context index and span sequence number together
   are the span context.
2. **Propagation (application).** The queue item carries the span context of the producer span which created it:
   `{context, span_seq}`, captured where the item is pushed. Plus the value and, if needed, the producer timestamp.
3. **Link (library or application).** The consumer span which processes the item records the span context of the item, for example
   as `<context>.link_ctx` and `<context>.link_seq`, measured inside the consumer span.
4. **Flows (xcpclient).** xcpclient remembers the begin timestamp and track of recent producer spans by span context. For each link
   sample it writes a flow v1 pair: `"s"` at the producer span, `"f"` with `"bp":"e"` at the consumer.

The decision was open at this point: how the span id and the link are recorded on the target.

- A) Signal naming convention: plain measured signals in existing events (`DaqEventCtxVar`), xcpclient finds them by name, like
  it finds `.span`, `.level`, `.span_dt`. No library change, but the application has to maintain the sequence numbers.
- B) Built into `DaqSpan`: `.span_seq` in the spans event, and a variant of `DaqSpan` which takes a link
  (for example `DaqSpanLinked(process, item.link)`). Cleaner API, library change.

Other things to decide or to know:

- Where the `"s"` event is placed. The begin timestamp of the producer span works, if no nested span begins at the same
  timestamp (the innermost slice wins). Alternative: a separate event at the push, inside the producer span but outside nested spans.
- Flow ids in the file must be unique. A running counter in xcpclient is enough, the span context is only needed for matching.
- If the producer span was not measured (measurement started later, sample lost), the link can not be resolved, xcpclient
  counts and drops it.
- xcpclient has to keep the producer spans until their items are consumed, a bounded map is enough. With a stall the
  distance can be long.
- With the context of the producer attached in the consumer (`xcp::Scope`), the consumer span would be in the producer track,
  concurrent with the producer thread. This needs `OPTION_DAQ_SPAN_THREAD`. Without it, the consumer span is in the `Mainloop`
  track, which is the clearer picture.

## Pseudo code with the trace records

The target never writes JSON. The `emit(...)` lines show which records xcpclient writes for the samples measured at this point.
Numbers are from the example trace `flow_v1.json`: the 5th `calc` of `SigGen1` (begin 32000 us) is processed by the main loop
after the stall, at 60100 us. Process ids: `SigGen1` = 1, `SigGen2` = 2, `Mainloop` = 3, track `spans` = `tid` 1.

### Producer: signal generator task (thread of SigGen1, context SigGen1)

```
struct QueueItem {
    double value;
    SpanContext link;           // {context, span_seq} of the producer span, e.g. {SigGen1, 9}
};

SignalGenerator::Task():
    Scope scope(context_)       // current context SigGen1

    loop:
        span calc begin                                  // span_seq = ++SigGen1.span_seq = 9 (calc and clip count)
            // sample SigGen1.spans: span=calc, level=1, span_seq=9, t=32000
            // xcpclient: remember begin of (SigGen1, 9) at pid 1, tid 1, ts 32000

            v = waveform(time)

            span clip begin                              // span_seq = 10, t=33500
                v = clip(v)
            span clip end                                // t=34500
                emit {"ph":"X","pid":1,"tid":1,"name":"clip","ts":33500,"dur":1000}

            queue.push({ value: v, link: current_span_context() })    // {SigGen1, 9}, t=34800
            DaqEventCtxVar(siggen, value_)               // complete stream on the producer side, as today
                emit {"ph":"C","pid":1,"name":"SigGen1.value_","ts":34800,"args":{"SigGen1.value_":42.0}}

        span calc end                                    // t=35000
            emit {"ph":"X","pid":1,"tid":1,"name":"calc","ts":32000,"dur":3000}

        sleep(delay_us)
```

### Consumer: main loop (main thread, context Mainloop)

```
main loop:
    Scope scope(mainloop_context)     // current context Mainloop

    loop:
        span drain begin                                 // t=60000
            while (item = queue.pop()):
                span process begin, link = item.link     // t=60100, link {SigGen1, 9}
                    // sample Mainloop: span=process, level=2, link_ctx=SigGen1, link_seq=9
                    // xcpclient: look up begin of (SigGen1, 9) -> pid 1, tid 1, ts 32000, new flow id 5
                    emit {"ph":"s","pid":1,"tid":1,"name":"queue","cat":"flow","id":5,"ts":32000}
                    emit {"ph":"f","pid":3,"tid":1,"name":"queue","cat":"flow","id":5,"ts":60100,"bp":"e"}

                    sum += item.value
                span process end                         // t=60900
                    emit {"ph":"X","pid":3,"tid":1,"name":"process","ts":60100,"dur":800}

            DaqEventCtxVar(mainloop, sum, queue_len)
                emit {"ph":"C","pid":3,"name":"Mainloop.sum","ts":67300,"args":{"Mainloop.sum":12.5}}
        span drain end                                   // t=67300
            emit {"ph":"X","pid":3,"tid":1,"name":"drain","ts":60000,"dur":7300}

        sleep(15000)
```

The `"f"` event at the begin timestamp of `process` should bind to `process`, the innermost slice there (not checked, whether a
slice encloses its own begin timestamp). In `flow_v1.json` it is placed in the middle of the slice (60500), which avoids the question.

### The same with flow format v2

Instead of the `"s"` and `"f"` events, the two slices get the flow fields:

```
emit {"ph":"X","pid":1,"tid":1,"name":"calc","ts":32000,"dur":3000,"bind_id":"0x5","flow_out":true}
emit {"ph":"X","pid":3,"tid":1,"name":"process","ts":60100,"dur":800,"bind_id":"0x5","flow_in":true}
```

Here `bind_id` has to be known when `calc` is written at its end, so it must be derived from the span context
(for example from context index and span_seq), not from a counter of resolved links.

### Metadata, written once per context

```
emit {"ph":"M","pid":1,"name":"process_name","args":{"name":"SigGen1"}}
emit {"ph":"M","pid":1,"tid":1,"name":"thread_name","args":{"name":"spans"}}
emit {"ph":"M","pid":3,"name":"process_name","args":{"name":"Mainloop"}}
emit {"ph":"M","pid":3,"tid":1,"name":"thread_name","args":{"name":"spans"}}
```
